# Likely Interview Questions and Answer Points

| Question | Concise answer points |
| --- | --- |
| Why use a PI controller? | Proportional action responds to current speed error; integral action removes steady-state error in this simple model. A derivative term was unnecessary for the demo and would add noise sensitivity and tuning complexity. |
| Why is the loop period 10 ms? | It is a fixed educational simulation step that is much shorter than the model's 0.35 s time constant. The host executable runs as fast as it can and advances a synthetic timestamp; it is not a real-time scheduler. On hardware, the period would be selected from plant dynamics and measured execution time, then scheduled and validated locally. |
| How does anti-windup work? | The controller computes an integral candidate. It stores that candidate inside the PWM range or when the error would drive a saturated output back toward the valid range. Otherwise the stored integral stays unchanged, while the candidate command is clamped to the actuator limit so the output can still reach exactly 0% or 100% without retaining excess integral state. |
| What numeric edge cases are handled? | ADC values must stay in the 12-bit range; sample time and gains must be finite and valid; overflow is rejected; non-finite RPM conversion returns a safe ADC value; simulated PWM clamps to 0-100% and treats non-finite commands as zero. |
| Why put scenarios in their own module? | The controller should react to inputs without knowing why they changed. Scenario generation owns fault injection, the motor model owns physical response, and the monitor owns fault classification. This keeps modules testable and avoids scattered demo conditions. |
| How is a sensor disconnect detected? | The scenario supplies an out-of-range measured-speed ADC. Input validation in the local controller commands zero PWM. The separate monitor maps that state to a latched `F101_SENSOR_SIGNAL_INVALID` event. |
| How is a stall detected? | The monitor requires target at least 1000 RPM, measured speed no more than 25% of target, PWM at least 70%, and 750 ms persistence. It exposes Warning before Fault. These are transparent demo assumptions that require real commissioning data before production use. |
| Could normal startup trigger the stall rule? | The PWM threshold and persistence reduce that risk, and the current startup uses less than 70% duty. A production design would test startup, load changes, sensor noise, and operating modes and might add mode-specific thresholds or current feedback. |
| Why does fault state latch? | A transient return to normal telemetry should not silently clear an important machine event. This demo resets state only when a new run is initialized. Real reset behavior would require an approved local machine sequence. |
| Is the dashboard controlling the motor? | No. It replays committed telemetry produced by C and has no write path to PWM, GPIO, the controller, or a remote API. Start, Pause, and Reset control playback only. |
| Why not run the controller in JavaScript or an industrial app platform? | Browser scheduling and networks are unsuitable for the deterministic 10 ms path. A platform is valuable for visualization, workflow, records, and integration, while control and safety stay local. |
| Is this integrated with Tulip? | No. It is a standalone portfolio demo. Its JSON Lines or CSV telemetry and HAL boundary illustrate a credible future gateway path, but no Tulip API, connector, or official integration is implemented. |
| What would real hardware change? | Replace the simulated HAL with board drivers, introduce scheduled execution, acquire real sensor and current data, characterize timing, tune with measured plant behavior, and add independently validated safety hardware and procedures. The interfaces and host tests provide a starting seam. |
| What is deterministic about the demo? | Scenario times, control period, model parameters, and calculations are fixed. There is no randomness or wall-clock input. Repeated full runs produce the same telemetry values and are checked by tests. |
| How was the dashboard data produced? | `make dashboard-data` executes each C scenario in JSON Lines mode and overwrites the three committed data files. JavaScript only parses and replays those records. |
| What does the simulated AI assistant actually do? | It selects predefined text from the fault code and summarizes recent telemetry. It is clearly labeled as a rules-based mock. A production assistant would need read-only, document-restricted access, sources, uncertainty, human confirmation, and complete logging. |
| How did you use AI responsibly while developing this? | AI output was treated as untrusted. The strict build and tests were retained, verification is recorded in `AI_USAGE.md`, and visual or owner review that has not happened is explicitly pending. I would explain and review each important decision before accepting it. |
| What would you improve next? | Add current and torque evidence, noisy-sensor tests, persistent event storage, role-aware workflows, a real local gateway protocol, and commissioning tools. I would avoid adding these until the small deterministic version is understood and validated. |
