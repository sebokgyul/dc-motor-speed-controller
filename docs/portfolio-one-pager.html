A deterministic C motor-control simulation extended with machine monitoring, structured telemetry, operator workflows, and a read-only static dashboard.

Repository github.com/sebokgyul/dc-motor-speed-controller

Manufacturing problem

A controls console exposes numbers but may not explain machine state, fault evidence, or safe next steps to an operator. This project adds that supervisory context without moving time-sensitive control into the browser.

Operator-focused result

Replay Normal, Sensor Disconnect, and Mechanical Jam scenarios; compare target and measured RPM; inspect PWM and state transitions; then follow a concise, safety-conscious fault workflow.

Key engineering decisions

Keep control localThe fixed 10 ms simulated PI path models a task that would be scheduled locally and would not depend on UI, network, or assistant latency.
Separate causes from reactionsScenarios inject conditions; the controller reacts to inputs; the monitor classifies machine state.
Require sustained evidenceStall detection warns first, then latches after 750 ms of low speed and high PWM.
Make data reproducibleThe dashboard replays committed JSON Lines regenerated from the C executable.

Sensor Disconnect

F101_SENSOR_SIGNAL_INVALID

Out-of-range ADC input causes an immediate local input fault and zero PWM. The valid target remains visible as diagnostic context.

Mechanical Jam

F201_MOTOR_STALL

A documented monitor checks target, speed ratio, drive effort, and persistence before latching a local simulated stop request.

Bounded advisory assistant concept

The UI contains a clearly labeled deterministic mock, not a language-model integration. A production agent would be restricted to read-only telemetry and approved documents, show sources and uncertainty, require human confirmation, log recommendations and decisions, and have no direct actuator control.
