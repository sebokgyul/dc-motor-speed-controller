# Three-Minute Interview Demo Script

## Before the interview

Run `make clean && make && make test && make dashboard-data`, then serve the dashboard with `python3 -m http.server 8000 --directory docs`. Open <http://localhost:8000>, keep the terminal available, and reset the dashboard to the Normal scenario.

## 0:00-0:25: Frame the problem

**Show:** Dashboard header and scenario controls.

**Say:** "This is my Connected Motor Monitoring and Operator Assistance Demo. The manufacturing problem is that useful controller data is often too technical for an operator. I kept the motor control in C, then added structured machine state, fault evidence, and a safe operator workflow. This is a standalone simulation, not a Tulip integration."

## 0:25-0:55: Explain the boundary

**Show:** The Control Boundary card, then briefly point to `docs/architecture.puml` if useful.

**Say:** "This host simulation advances the PI loop in fixed 10 millisecond steps. On hardware, that time-sensitive task would be scheduled locally because browser and network timing are not deterministic. The dashboard is supervisory: it reads telemetry, charts state, and guides the operator. It has no path to PWM or GPIO. Any AI assistance is also advisory only, so safety-critical control stays at the machine."

## 0:55-1:25: Run normal operation

**Show:** Select Normal and press Start. Point to target RPM, measured RPM, PWM duty, chart, and event log.

**Say:** "The target follows a fixed production profile. The measured speed responds through a first-order motor model, and the PI controller adjusts duty. This is not JavaScript control logic. The browser replays JSON Lines generated by the C executable, so the run is deterministic and testable."

## 1:25-2:10: Demonstrate fault handling

**Show:** Press the Guided Interview Demo button, or select Mechanical Jam and press Start. At 5.5 simulated seconds, point to falling measured speed and rising PWM. At 6.0 seconds, point to Warning; at 6.7 seconds, point to Fault and zero PWM after the local stop request.

**Say:** "The scenario module injects a generic load; there are no jam conditions inside the PI controller. A separate monitor looks for target above 1000 RPM, speed below 25 percent of target, and PWM above 70 percent. It warns first and requires 750 milliseconds of sustained evidence before latching the stall. The local simulation then requests a stop. Those thresholds are documented demo assumptions, not production settings."

## 2:10-2:40: Show operator assistance

**Show:** Fault code, approved response, observation field, and simulated assistant card.

**Say:** "The fault opens a safety-conscious workflow: confirm a safe state, inspect only what the role permits, review evidence, record an observation, and escalate when it cannot be cleared safely. The assistant response is explicitly a deterministic mock, not a real language model. It shows the intended guardrails: read-only telemetry, approved documents, visible sources, uncertainty, human confirmation, and no actuator control."

## 2:40-3:00: Close with engineering evidence

**Show:** Terminal output from `make test`, then return to the dashboard.

**Say:** "The C99 build keeps warnings as errors. Tests cover PI behavior, anti-windup, non-finite inputs, ADC and PWM boundaries, scenario timing, stall latching, deterministic full runs, and telemetry fields. A future gateway could send slower telemetry to an industrial platform such as Tulip, while the 10 millisecond loop and safety functions remain local."

## Optional sensor-fault alternative

If asked about signal validation, replay Sensor Disconnect. At 5.5 seconds the measured ADC is invalid, the controller enters Input Fault immediately, PWM becomes zero, measured RPM is shown as unavailable, and the dashboard displays `F101_SENSOR_SIGNAL_INVALID`. Explain that preserving the valid target in telemetry helps diagnosis without presenting an invalid speed sample as zero.
