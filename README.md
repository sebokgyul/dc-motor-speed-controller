# Connected Motor Monitoring & Operator Assistance Demo

This portfolio project turns a small DC motor control simulation into an operator-focused manufacturing story. A C program runs a deterministic motor, sensor, and PI-control simulation. It emits telemetry that a static dashboard replays to explain normal operation, fault detection, and safe operator assistance.

The project is not connected to Tulip and does not claim an official Tulip integration. It demonstrates an architecture that could later send supervisory data to an industrial operations platform such as Tulip while retaining time-sensitive and safety-related behavior at the machine.

## Manufacturing problem

A motor can stop meeting its target because of a failed speed signal, an obstruction, excess load, or another machine issue. A raw controller console is useful to an engineer but does not give an operator a clear machine state, event history, or approved next steps.

This demo addresses that communication gap. It preserves the local feedback controller and adds deterministic scenarios, machine monitoring, structured telemetry, and a browser interface that turns control data into an understandable operator workflow.

## Demo story

The operator starts with a normal production cycle and sees measured speed follow changing target speeds. The operator can then replay one of two injected faults:

- A disconnected speed sensor creates an invalid ADC input. The local controller enters an input-fault state and commands zero PWM.
- A mechanical jam loads the motor until measured speed remains below 25% of target while PWM is at least 70%. The monitor shows a warning, confirms the condition for 750 ms, latches a stall fault, and requests a local simulated stop.

Every run is generated by the same C executable using a fixed 10 ms time step. There is no random input, wall-clock dependency, or browser implementation of the control algorithm.

## Business value

- Makes machine state and control response understandable to an operator, not only to a controls engineer.
- Separates a transient warning from a confirmed fault to reduce premature diagnosis.
- Gives faults a code, message, timestamp, evidence, and consistent safe workflow.
- Provides reproducible records for demonstrations, automated tests, and future event-history analysis.
- Shows how a machine can expose useful telemetry without moving real-time control into a cloud or web application.

This is a learning project rather than a quantified production deployment, so it does not claim measured downtime or quality improvements.

## Architecture

The main data path is:

```text
Motor and speed sensor -> Simulated HAL -> Local PI controller
                                             |
                                             v
                              Telemetry and machine monitor
                                             |
                                             v
                                      Operator dashboard
```

The controller writes PWM through the HAL and the motor model returns speed feedback, forming the local loop. The scenario module supplies operator commands and simulated disturbances. The monitor consumes controller output but does not alter the PI calculation. On a confirmed fault it latches a local stop request in the simulation. The browser receives only committed telemetry records.

| Component | Responsibility |
| --- | --- |
| `motor_controller` | Convert ADC inputs, run the PI calculation, apply conditional-integration anti-windup, and fail safely on invalid input or configuration. |
| `motor_model` | Simulate a first-order motor response and a generic mechanical load. |
| `simulated_hal` | Represent ADC, GPIO, and bounded PWM hardware interfaces. |
| `scenario` | Generate normal, sensor-disconnect, and mechanical-jam inputs at defined timestamps. |
| `machine_monitor` | Classify Disabled, Running, Warning, and Fault states and latch sensor or stall faults. |
| `simulation` | Run the modules at a deterministic 10 ms step and publish telemetry snapshots. |
| `telemetry` | Serialize records as a readable table, JSON Lines, or CSV. |
| `docs/` dashboard | Replay read-only C output, chart speed, record UI events, and present operator guidance. |

The complete PlantUML component view is in [`docs/architecture.puml`](docs/architecture.puml).

## Why real-time control remains local

The simulation advances the PI controller in fixed 10 ms steps, modeling a time-sensitive task that would be scheduled locally every 10 ms on hardware. Its safe output behavior must not depend on browser rendering, network latency, cloud availability, or an advisory assistant. ADC validation, PWM limits, controller reset behavior, and the simulated fault response therefore remain in the local C machine-control layer. This host simulation does not claim wall-clock real-time scheduling or deadline validation.

The dashboard is supervisory. It can consume telemetry, visualize state, record events, and guide an operator, but it has no command path to PWM, GPIO, or the motor. The simulated AI assistant is advisory only. In real equipment, safety-rated interlocks and emergency functions would also remain local and would require appropriate hardware, risk assessment, and validation beyond this demo.

## Dashboard and fault scenarios

| Scenario | Injection | Expected supervisory result |
| --- | --- | --- |
| Normal | Defined target changes with a healthy sensor and no added load. | Disabled and Running states; no fault. |
| Sensor Disconnect | Measured-speed ADC is set outside its valid 12-bit range at 5.5 s. | Immediate controller input fault, unavailable measured RPM, zero PWM, and `F101_SENSOR_SIGNAL_INVALID`. |
| Mechanical Jam | Generic motor load increases to 100% at 5.5 s. | Warning during sustained stall evidence, then latched `F201_MOTOR_STALL` and a local simulated stop request. |

The stall monitor assumes that a target of at least 1000 RPM is meaningful, measured speed at or below 25% of target is abnormal, PWM at or above 70% indicates strong drive effort, and the condition must persist for 750 ms. These are demonstration thresholds, not validated settings for real machinery. They would need commissioning data, nuisance-trip analysis, and a safety review before hardware use.

For either fault, the dashboard asks the operator to:

1. Confirm that the machine is in a safe state.
2. Inspect the sensor connection or physical obstruction indicated by the fault.
3. Check the displayed telemetry and fault code.
4. Record the operator's observation.
5. Escalate to maintenance if the issue cannot be cleared safely.

The workflow never recommends bypassing a safety mechanism or restarting equipment that is not known to be safe.

## AI assistant and guardrails

The dashboard includes a **simulated AI-assistant response**. It is a deterministic, rules-based presentation based on the current fault code, recent telemetry, and [`docs/troubleshooting-samples.md`](docs/troubleshooting-samples.md). It is not a language model and is not represented as one.

A production advisory assistant could be grounded in approved maintenance documents, but it should have all of these controls:

- Read-only access to relevant telemetry.
- Access only to approved documentation.
- No direct actuator or controller access.
- Visible source references for recommendations.
- Explicit uncertainty disclosure.
- Human confirmation before operational action.
- Logging of recommendations and operator decisions.

An assistant must not be part of a safety function. Safety-critical control remains in the local machine-control layer.

## Build and test instructions

Requirements are a C99 compiler and `make`. The existing strict flags are retained: `-std=c99 -Wall -Wextra -Wpedantic -Werror -O2`.

```sh
make clean
make
make test
```

The test executable covers controller behavior, ADC conversion, numeric faults, state reset, anti-windup, HAL limits, motor load, scenario boundaries, stall monitoring, full deterministic simulations, and telemetry fields.

## Running or regenerating the demo

The original no-argument command still runs the normal scenario with readable table output:

```sh
./build/motor_control
```

All scenario and format combinations use the same executable:

```sh
./build/motor_control --scenario normal --format table
./build/motor_control --scenario normal --format jsonl
./build/motor_control --scenario normal --format csv
./build/motor_control --scenario sensor-disconnect --format table
./build/motor_control --scenario mechanical-jam --format table
```

Table records are shown every 500 ms. JSON Lines and CSV records are emitted every 100 ms. Each record contains timestamp, target RPM, measured RPM, PWM duty, controller state, machine state, fault code, and fault message. An invalid speed measurement is represented as `null` in JSON Lines, an empty CSV field, and `--` in the readable table rather than as a plausible zero-RPM reading.

Regenerate all committed dashboard records from the C simulation:

```sh
make dashboard-data
```

Serve the static dashboard locally, then open <http://localhost:8000>:

```sh
python3 -m http.server 8000 --directory docs
```

The page uses only local HTML, CSS, JavaScript, and telemetry files. It does not require an API key, package install, external API, or internet connection. Opening `docs/index.html` directly is not supported because browsers commonly block local `fetch` requests; use the local server command above.

## Limitations and possible real-hardware integration

The motor is a first-order educational model. It does not model current, torque, inertia changes, friction, electrical dynamics, ADC noise, dropped samples, thermal behavior, or real safety circuits. The jam is represented as a generic load disturbance. The browser event log and operator note are not persisted. Fault reset is represented by starting a fresh deterministic run rather than a validated machine reset sequence.

A real-hardware path could replace `simulated_hal` with board-specific ADC, PWM, and GPIO drivers while retaining controller interfaces and host tests. Additional machine inputs could include current, drive status, guard state, and safety-interlock state. A gateway could publish slower supervisory telemetry and events to an industrial platform such as Tulip. That platform could visualize status, manage workflows, and store records, but it would not run the 10 ms PI loop or replace safety-rated local controls.

This repository is not currently connected to hardware, a production data source, or Tulip.

## Responsible use of AI during development

AI assistance was used to inspect code, propose edge cases, implement scoped changes, and draft tests, dashboard code, and documentation. Suggestions were treated as untrusted until compiled, tested, or explicitly marked for manual review. The original strict compiler settings and test expectations were not weakened to accept generated code.

[`AI_USAGE.md`](AI_USAGE.md) records each major contribution, the engineering decision made, verification actually performed, and pending owner review. Visual browser review, interview rehearsal, and any real-hardware claims remain manual steps and are not represented as complete until they occur.
